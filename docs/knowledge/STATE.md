# Project state

**The board.** Where every module is in the pipeline, and which client documents have been read.
Checked automatically at the start of every session, so work picks up where it stopped — even weeks
later, even in a different tool.

Maintained by the skills as they run. If you are unsure what to do next, ask — or run `whats-next`.

## Input documents

Every file in `docs/knowledge/input/`. The hash is how a returning session knows a document is new
or has been edited since it was read. `grill-me` adds a row after parsing a document.

> Recording a hash: `shasum -a 256 docs/knowledge/input/<file> | cut -c1-8`
> A document whose current hash is not in this table is **unparsed** — its contents have never been
> turned into requirements. The session-start check will say so.

**Rules for this table**

- A module reaches `done` on a phase only when that phase's skill says its checklist passed.
- Never mark a phase `done` you did not actually run. A wrong board is worse than no board — the
  next session trusts it.
- `n/a` is legitimate (a module with no UI, a change with no schema). Note why in Log.
- Only **one** module should be `wip` across the build phases at a time. Finishing beats starting.
